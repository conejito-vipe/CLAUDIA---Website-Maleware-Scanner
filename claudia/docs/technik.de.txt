## g:ablauf | Wie ein Befehl zum Server kommt
Jede Prüfung ist ein kurzes Bash-Skript. Das Programm schickt es über die verschlüsselte SSH-Verbindung (paramiko) als einen einzigen Befehl an den Server und liest die Ausgabe. Es gibt keinen Daemon und nichts bleibt auf dem Server zurück.
- wrap_script: wechselt in den Seitenordner, setzt LC_ALL=C und startet das Skript mit niedriger Priorität (nice -n 15), damit die Seite nicht langsamer wird.
- sq: setzt jeden Wert, der in einen Befehl eingebaut wird, in sichere Anführungszeichen (shlex.quote). So kann kein Dateiname oder Wert zusätzliche Befehle einschleusen.
- Runner.sh und SSHRunner.run: führen den Befehl aus, begrenzen Dauer und Ausgabemenge und liefern Ausgabe, Fehlertext und Exit-Code zurück. Ein Zeitlimit beendet hängende Befehle.
- Ctx.sh: die Stelle, über die jede Prüfung ihre Skripte startet. Ist kein Server verbunden, wird die Prüfung übersprungen.
Prüfungen sind rein lesend: Sie enthalten nur Lesebefehle (find, grep, stat, cat, SELECT). Änderungen am Server gibt es nur über die Aktionen und nur nach Vorschau und Bestätigung.
## g:datenbank | Wie die Datenbank abgefragt wird
Das Programm verbindet sich nicht selbst mit der Datenbank, sondern ruft auf dem Server das Programm mysql (oder mariadb) auf. Die Zugangsdaten stehen in der configuration.php bzw. wp-config.php und werden dort gelesen (_read_cfg).
- Das Passwort steht nie in der Befehlszeile (dort wäre es für andere Konten über die Prozessliste sichtbar). Es wird als erste Zeile über stdin übergeben, mit read in MYSQL_PWD gelesen und exportiert.
- _check_vars prüft vorher, dass Benutzer, Datenbankname und Host nur erlaubte Zeichen enthalten.
- #__ im SQL ist der Platzhalter für das Tabellenpräfix und wird vor dem Aufruf ersetzt.
- parse macht aus der mysql-Ausgabe (Tabulator-getrennt) eine Liste von Zeilen. Fehlertexte werden vorher von Passwörtern bereinigt.
Alle Abfragen der Prüfungen sind SELECT oder SHOW. Schreibende SQL-Befehle gibt es nur in zwei Aktionen (JCE-Profile löschen, Registrierung in WordPress ausschalten), jeweils nach Sicherung der betroffenen Tabelle.
## g:sicherung | Wie die Sicherung entsteht
Aktionen mit dem Merkmal Sicherung vorher legen zuerst eine Sicherung im Home-Verzeichnis des Servers an (Ordner claudia-sicherung-<Datum>, Rechte 700). Ohne gültige Sicherung bricht die Aktion ab, bevor etwas verändert wird. Kleinere Aktionen legen stattdessen eine gezielte Sicherung nur der betroffenen Dateien oder Tabelle an (_mkdir_backup).
- make_backup prüft zuerst den freien Platz (df gegen du der Seite, mindestens das 1,3-fache), legt den Ordner mit mkdir -p -m 700 an, sichert die Datenbank (_db_dump_script, Passwort wieder über stdin) und dann die Dateien als tar.gz (ohne Bilder, Cache, tmp und Logs; bei WordPress ohne uploads, cache, upgrade).
- Danach wird das Archiv mit tar tzf geprüft und die Größe beider Dateien kontrolliert (zu klein = Abbruch).
- _home_dir bestimmt das Home-Verzeichnis des Server-Kontos.
Die Sicherung enthält auch infizierte Dateien. Sie darf nie in einen öffentlich erreichbaren Ordner kopiert werden.
## g:programmupdate | Wie sich das Programm aktualisiert
Beim Start fragt CLAUDIA im Hintergrund die Release-Seite des Projekts auf GitHub ab (eine einzige https-Anfrage, ohne Netz passiert nichts). Installiert wird nur nach Rückfrage im Fenster.
- appupdate.check liest tag_name, Release Notes und das Paket CLAUDIA_v<Version>.zip; nur Downloads unter github.com/<Projekt>/releases/download/ werden akzeptiert. Die Prüfsumme kommt aus dem Digest des Pakets oder aus einer Zeile "SHA-256: ..." in den Release Notes. Ohne Prüfsumme wird nicht automatisch installiert.
- appupdate.verify_package vergleicht SHA-256, prüft die ZIP-Datei (testzip), verbietet Pfade mit .. oder Laufwerksangabe und verlangt, dass claudia/__init__.py genau die erwartete Version enthält.
- appupdate.backup packt den Programmordner (ohne .venv) nach %APPDATA%\CLAUDIA\update\sicherung_<Version>.zip; frühere Sicherungen werden ersetzt.
- appupdate.install schreibt jede Datei über eine Nebendatei und os.replace. Schlägt etwas fehl, spielt restore die Sicherung zurück und entfernt neu angelegte Dateien; update.log enthält jeden Schritt.
- start.bat, start.command und install.command werden erst nach dem Beenden ersetzt (finish_code in einem losgelösten Prozess), weil eine laufende Startdatei sonst mitten im Lauf geändert würde. Derselbe Prozess startet CLAUDIA danach neu.
- Von Hand zurück: die Sicherung aus %APPDATA%\CLAUDIA\update in den Programmordner entpacken (Dateien ersetzen).
## g:haertung | Schutzfunktionen und ihre Tests
Alles, was Vertrauen herstellt oder Schaden begrenzt, ist zentral und mit Tests samt Wirksamkeitsbeweis abgesichert: Wird die Funktion absichtlich entschärft, muss der zugehörige Test scheitern (tests/test_sicherheitsfunktionen.py).
- util.sq setzt jeden Wert für die Shell des Servers in Anführungszeichen; db.validate_vars erlaubt für Datenbankname, Präfix, Benutzer, Host und Socket nur gewöhnliche Zeichen und endet mit \Z, damit auch ein angehängter Zeilenumbruch abgelehnt wird.
- util.parse_xml liest fremdes XML nur ohne DOCTYPE/ENTITY, bis 3 MB und gibt bei jedem Fehler None statt einer Ausnahme zurück. util.digits akzeptiert nur ASCII-Ziffern.
- util.mask_secrets schwärzt Zugangsdaten; der Wert ist auf 4096 Zeichen begrenzt, damit die Laufzeit linear bleibt.
- Der lokale Server prüft Host und Origin, verlangt Sitzungs-Cookie und Kopf X-Claudia, begrenzt die Anfragegröße und gibt Dateien nur aus einer festen Liste aus.
## g:dashboard | Wie das Dashboard den Verlauf führt
Nach jeder vollständig durchgelaufenen Prüfung und nach jeder ausgeführten Aktion schreibt CLAUDIA einen kurzen Eintrag in die Datei verlauf.json im Datenordner. Das Dashboard liest nur diese Datei (und auf Wunsch den Bestand an Sicherungen und Quarantäne auf dem Server) und verändert nichts.
- Gespeichert werden nur Zeit, Seite (Host und Ordner), CMS, Version, Zählstände, die Kurzbezeichnungen der Warnungen und kritischen Funde sowie ausgeführte Aktionen mit Ergebnis. Keine Passwörter, keine Dateiinhalte, keine Übertragung nach außen. Abgebrochene Prüfungen und Prüfungen mit Fehler werden nicht gespeichert.
- Ein Fund gilt im Vergleich nur dann als behoben, wenn die zugehörige Prüfung beim zweiten Mal wirklich gelaufen ist (Feld ran). Wurde sie nicht gewählt oder übersprungen, steht der Fund unter "nicht geprüft", nicht unter "behoben".
- Grenzen: 400 Prüfungen und 600 Aktionen insgesamt; je Seite behalten die letzten 12 Prüfungen ihre Fundliste, ältere nur die Zählstände. Eine kaputte oder fremde Datei führt zu einem leeren Verlauf, nie zu einer Ausnahme; Schreiben und Lesen laufen unter einer Sperre.
- Hinweise: letzte Prüfung älter als 30 Tage, noch keine oder eine alte Sicherung mit CLAUDIA.
- Nachkontrolle: Nach der letzten erfolgreichen Bereinigung (z. B. Schadcode entfernt, Konten gesperrt) gilt eine Prüfung ab drei Tagen später als Nachkontrolle; die Prüfung direkt danach ist die Erfolgskontrolle. Fehlt sie, erscheint der Hinweis.
- Sicherung prüfen (verify_backup): nur lesend gzip -t und tar tzf für die Dateien einer Sicherung; der Name muss zu den Sicherungen des Programms passen, sonst wird nichts ausgeführt.
- Export: export_csv entschärft Zellen, die mit =, +, - oder @ beginnen; der Bericht schreibt alle Texte HTML-sicher. support.build lässt Passwörter, Serveradresse, Benutzernamen, Seitenordner und die Texte der Funde weg.
- Verwaltung: Sicherung anlegen, alte Sicherungen löschen, Quarantäne zurückholen oder löschen laufen über dieselben, getesteten Aktionen wie "Lösungen auf Knopfdruck" (Vorschau der Befehle, Bestätigung, Ausführung). Eine Vollsicherung wird bewusst nicht automatisch zurückgespielt, weil das den aktuellen Stand der Seite überschreibt und sich nicht rückgängig machen lässt.
## g:signatur | Digitale Unterschrift für Updates und Wissensdaten
Programm-Updates und neue Wissensdaten können mit einer Ed25519-Unterschrift geprüft werden. Das Programm kennt nur den öffentlichen Schlüssel (signatur.PUBLIC_KEYS) und kann damit prüfen, aber nichts unterschreiben; der private Schlüssel liegt nur beim Autor (tools/signieren.py).
- Solange kein öffentlicher Schlüssel eingetragen ist, ist die Prüfung nicht aktiv: Es gilt unverändert die Prüfsumme, es wird nichts zusätzlich geladen, und abgelegte Wissensdaten werden nie benutzt.
- Ist ein Schlüssel eingetragen, wird ohne gültige Unterschrift nichts installiert und nichts übernommen. Jede Abweichung ist ungültig, auch ein einziges verändertes Zeichen, eine unbekannte Schlüssel-ID oder ein falscher Zweck; verify wirft nie eine Ausnahme.
- Unterschrieben wird "CLAUDIA-SIG1", der Zweck (release oder wissen) und die Datei. Dadurch gilt eine Unterschrift für ein Paket nie für Wissensdaten und umgekehrt.
- Programm-Update: Neben CLAUDIA_vX.Y.Z.zip liegt CLAUDIA_vX.Y.Z.zip.sig auf der Release-Seite; geladen wird nur von Adressen dieses Projekts.
- Wissensdaten: wissen/advisories.json mit wissen/advisories.json.sig im Repository. Eine Fassung wird nur übernommen, wenn sie gültiges JSON mit allen Abschnitten der mitgelieferten Fassung ist und einen neueren Stand hat; beim Lesen wird die Unterschrift jedes Mal erneut geprüft.
## g:protokoll | Wie das Statusfenster mitliest
Während einer Aktion läuft jeder Befehl durch die Hülle Traced. Sie meldet Befehl und Antwort an das Statusfenster, damit du live siehst, was auf dem Server passiert.
- mask ersetzt Passwörter, Download-Schlüssel und Tokens durch *** (bekannte Geheimnisse und Muster wie key=..., token=...), bevor etwas angezeigt oder im Bericht gespeichert wird.
- Die Ausgabe wird auf die letzten 2.500 Zeichen gekürzt, ein Zeitlimit wird als Fehler gemeldet.
## g:extern | Wie der externe Modus arbeitet
Im externen Modus gibt es keinen Runner (kein SSH). App._connect_external setzt conn auf {mode: none, external: true, url, host} und ruft extern.detect_site; Settings.extern lässt Engine.run alle Prüfungen auslassen, die weder extern=True noch needs=local haben.
- Erkennung: extern.detect() zählt gewichtete Merkmale (Generator, Ordner, Kopfzeilen, Cookies, Standardadressen). Ein System gilt nur bei Gewicht ab 3 und mindestens 2 Vorsprung als erkannt, sonst bleibt es leer.
- Weiche 404: gather() ruft eine zufällige Adresse ab; liefert sie Status 200, werden Standardadressen mit gleicher Seite verworfen, und ext_files zählt Treffer nur, wenn die Seite abweicht. Zusätzlich braucht jede Datei eine Signatur im Inhalt.
- Versionen: parse_version() liest nur öffentliche Quellen; judge_version() nutzt die vorhandenen Bewerter je System und fällt bei fehlender Online-Quelle auf "info" zurück (CLAUDIA_OFFLINE: keine Abrufe).
- Grenzen: höchstens 25 Zusatzabrufe für Erweiterungen, Antworten werden auf 40 bis 60 KB begrenzt, nur https (Ausnahme lokale Adressen), Inhalte gefundener Dateien erscheinen nie im Ergebnis.
## a:backup_now | Vollständige Sicherung
Es läuft nur der Sicherungsschritt (siehe Grundlagen: Sicherung). Danach wird der Ordnername gemeldet. Auf dem Server wird nichts verändert außer dem neuen Sicherungsordner.
## a:fix_permissions | Schreibrecht für alle entfernen
Pro Datei aus der Prüfung: Rechte mit stat in rechte_vorher.txt festhalten, dann chmod o-w. Verweise (Symlinks) werden übersprungen. Es werden nur Dateien angefasst, die die Prüfung selbst gemeldet hat und die als Pfad zulässig sind (höchstens CHMOD_MAX Stück).
## a:fix_update_perms | Schreibrecht für den Besitzer wiederherstellen
Wie die Aktion davor, aber mit chmod u+rwX: Der Besitzer darf wieder schreiben, bei Ordnern auch betreten. Die alten Rechte stehen vorher im Protokoll rechte_vorher.txt.
## a:wp_remove_maintenance | Wartungsmodus beenden
Erst wird geprüft, dass .maintenance eine normale, kleine Datei ist und nur $upgrading = <Zahl>; enthält. Dann wird eine Kopie angelegt und erst nach geglückter Kopie gelöscht. Danach wird kontrolliert, dass die Datei weg ist.
## a:check_updates | Nach Updates suchen
Es werden nur Abfragen gestellt, nichts installiert: die Joomla-Kommandozeile (core:check-updates, update:extensions:check), danach die Liste der Updates aus der Datenbank und eine Gegenprobe direkt bei den Update-Servern der Hersteller.
## a:core_update | Joomla aktualisieren
Nach der Sicherung ruft das Programm die Joomla-Kommandozeile core:update auf (Zeitlimit 25 Minuten). Das Update selbst macht Joomla, das Programm prüft nur den Exit-Code und zeigt die Ausgabe.
## a:update_extensions | Erweiterungen aktualisieren
Nach der Sicherung wird für jede gewählte Erweiterung das Update-Manifest auf dem Server mit curl (nur https) geladen und die Download-Adresse der neuen Version herausgesucht (pick_download). Installiert wird mit extension:install --url der Joomla-Kommandozeile. Danach liest eine SQL-Abfrage die Version aus manifest_cache zur Kontrolle. Schlägt etwas fehl, folgen bis zu EXT_RETRIES Wiederholungen (Abhängigkeiten); Erweiterungen, deren Installer nicht über die Kommandozeile läuft, werden gemeldet und nicht wiederholt. Am Ende: update:extensions:check und cache:clean.
## a:clean_tmp | Temporäre Ordner leeren
Zuerst wird der ganze Inhalt der gewählten Ordner als tar.gz gesichert und mit tar tzf geprüft. Erst danach werden die Einträge gelöscht (index.html und .htaccess bleiben). Zum Schluss wird gezählt, was noch drin liegt.
## a:delete_old_backups | Alte Sicherungen löschen
Auf dem Server werden nur Ordner direkt in deinem Home gelöscht, deren Name mit claudia-sicherung- beginnt und die kein Verweis sind (rm -rf). Der Name muss zum festen Muster BACKUP_NAME_RE passen. Zusätzlich lassen sich Protokolle auf deinem Computer löschen (LOG_NAME_RE; das neueste Protokoll einer Aktion bleibt).
## a:remove_jce_profiles | Verdächtige JCE-Profile entfernen
Ein SELECT liest die gewählten Profile, die php in ihren Parametern enthalten. Standardprofile (SAFE_JCE_NAMES) werden nicht gelöscht, nur gemeldet. Vor dem Löschen wird die Tabelle wf_profiles als wf_profiles.sql.gz gesichert (nur auf deinen ausdrücklichen Wunsch ohne). Dann folgt ein DELETE mit denselben Bedingungen und ein COUNT zur Kontrolle.
## a:remove_shells | Web-Shells in Quarantäne verschieben
Du hakst in der Liste selbst an, welche Dateien verschoben werden (_picked_shell_files: nur Dateien, die die Prüfung gemeldet hat, oder PHP-Dateien im Upload-Ordner, nie außerhalb der Seite). Jeder Pfad wird geprüft (_safe_path), nur normale Dateien zählen, Verweise nicht, höchstens MAX_FILES je Lauf. Ordner ohne Schreibrecht werden vorab gemeldet und ausgelassen. _new_quarantine_dir legt ~/claudia-quarantaene-<Datum>/d mit Rechten 700 an (Abbruch ohne Änderung, wenn das Home-Verzeichnis im Seitenordner liegt) und eine Zugriffssperre. _quarantine_header schreibt den Kopf der Liste QUARANTAENE.txt. Das Skript QUAR_MOVE geht Datei für Datei vor: Ordner muss real in der Seite liegen, SHA-256, Rechte, Besitzer, Größe und Datum bestimmen, die Zeile in die Liste schreiben, dann mv -n in d/<Nr>.q (gleiches Dateisystem) bzw. cp -p, Prüfsumme vergleichen und erst dann das Original entfernen (anderes Dateisystem). Danach chmod 600 und ein Vergleich der Prüfsumme. Jede Datei meldet OK, UEBERSPRUNGEN, FEHLER oder HINWEIS; zum Schluss wird gezählt, was im Ordner d liegt. Nichts wird gelöscht.
## a:restore_quarantine | Dateien aus der Quarantäne zurückholen
Die Auswahl (Schlüssel q:<Ordner>/<Nr>) wird mit QUAR_KEY_RE geprüft; Ursprungspfad, Prüfsumme und Rechte liest das Skript QUAR_BACK selbst aus der Liste auf dem Server, nicht aus der Auswahl. Je Datei: Datei liegt noch in d/, die Liste gehört zu dieser Seite, der Ursprungspfad ist gültig (./..., kein ..), der Ursprungsordner existiert, liegt real in der Seite und ist beschreibbar, am Ursprungsort liegt nichts (auch kein Verweis) und die SHA-256 stimmt mit der Liste. Dann mv -n bzw. (anderes Dateisystem) cp -p, Prüfsumme vergleichen, Quelle entfernen; danach chmod mit den ursprünglichen Rechten, Vergleich der Prüfsumme und ein Eintrag in ZURUECK.txt. Trifft eine Bedingung nicht zu, meldet das Skript UEBERSPRUNGEN mit Grund und fasst die Datei nicht an. _parse_quar_lines wertet die Meldungen aus.
## a:delete_quarantine | Quarantäne-Ordner löschen
Die Auswahl (Schlüssel k:<Ordnername>) wird mit QUAR_NAME_RE geprüft. Das Skript QUAR_DEL prüft je Ordner: Name beginnt mit claudia-quarantaene-, kein Schrägstrich, Ordner liegt im Home-Verzeichnis und ist kein Verweis, die Liste QUARANTAENE.txt ist da und ihr Kopf nennt genau diesen Seitenordner. Erst dann rm -rf, danach die Kontrolle, dass der Ordner fehlt. Jede Meldung (OK, UEBERSPRUNGEN, FEHLER) wertet _parse_quar_lines aus. Nichts im Ordner wird geöffnet oder ausgeführt.
## a:reset_htaccess | Hauptdatei .htaccess auf den Standard zurücksetzen
Das Programm liest die .htaccess (_ht_read) und bestimmt die Standarddatei (ht_standard): bei Joomla htaccess.txt aus dem Original-Paket der Version (Prüfsumme geprüft), bei WordPress den Standardblock. ht_plan zerlegt die vorhandene Datei in Regeln und Blöcke "# BEGIN/END Name" und übernimmt eigene harmlose Regeln und Blöcke bekannter Plugins; Weiterleitungen auf fremde Domains, Handler-Zuweisungen und auto_prepend_file nicht. Die Vorschau ist ein Zeilenvergleich alt/neu. Vor dem Schreiben prüft das Skript, ob Ordner und Datei beschreibbar sind, kopiert die alte Datei als htaccess.vorher (cp -p, dann cmp) und schreibt rueckgaengig.txt. Nach dem Schreiben ruft _fetch_url die https-Startseite ab; bei einem Serverfehler (5xx) wird htaccess.vorher sofort zurückkopiert und der Abruf wiederholt. Ohne https-Adresse wird nichts verändert.
## a:remove_db_code | Eingeschleusten Code in der Datenbank entfernen
_dbcode_plan liest die gewählten Einträge (Tabelle, Spalte, Kennung) über die Datenbank-Zugangsdaten der Seite (g:datenbank), liefert den Wert hex-kodiert (höchstens DBCODE_MAX_HEX) und entfernt nur Skript- und Frame-Blöcke, die zu den Mustern der Prüfung passen. Übersprungen werden serialisierte WordPress-Werte (a:..., s:...), zu große Werte und Einträge ohne eindeutigen Treffer; der Grund wird je Eintrag protokolliert. Vor jeder Änderung schreibt das Programm für jeden Eintrag einen UPDATE-Befehl mit dem alten Wert in rueckgaengig.sql und prüft die Datei (Anzahl der Befehle, Prüfsumme); ohne gültige Sicherung bricht es ab. Danach wird jeder Eintrag erneut gelesen und mit dem erwarteten neuen Wert verglichen.
## a:block_php_uploads | PHP-Ausführung im Bilder-Ordner sperren
Das Programm prüft zuerst, dass die https-Adresse der Seite bekannt ist und der Ordner kein Verweis ist. Eine vorhandene .htaccess wird als htaccess.vorher gesichert (cp -p, dann cmp), dazu schreibt es rueckgaengig.txt. Danach hängt es den Block HTACCESS_NOPHP an bzw. legt die Datei neu an (Apache 2.2 und 2.4). Zum Prüfen legt es eine .txt- und eine .php-Datei mit zufälligem Namen und harmlosem Inhalt an und ruft beide per https ab (_fetch_url). Die Sperre gilt nur als wirksam, wenn die Textdatei ausgeliefert wird und die PHP-Datei nicht ausgeführt wird. Sonst (oder wenn der Abruf nicht möglich ist) stellt es den alten Stand wieder her. Die Testdateien werden in jedem Fall gelöscht.
## a:harden_headers | Sicherheits-Header setzen
Das Programm prüft zuerst, dass die https-Adresse der Seite bekannt ist und die .htaccess kein Verweis ist. Steht der Block '# CLAUDIA: Sicherheits-Header' schon darin, endet die Aktion ohne Änderung. Sonst wird die vorhandene .htaccess als htaccess.vorher gesichert (cp -p, dann cmp), dazu rueckgaengig.txt geschrieben und der Block angehängt (ht_block_text). Gesetzt werden nur die Header, die die Prüfung als fehlend gemeldet hat, aus einer festen Liste (nosniff, SAMEORIGIN, strict-origin-when-cross-origin); die Content-Security-Policy wird nie gesetzt. Danach ruft ht_block_verdict die Startseite einmal ab: Kommt ein Header nicht an oder liefert die Seite HTTP 500 oder höher oder ist sie nicht erreichbar, wird der alte Stand wiederhergestellt. Bei nginx (liest keine .htaccess) wird die Aktion gar nicht erst angeboten.
## a:harden_hsts | HSTS aktivieren
Ablauf wie bei den Sicherheits-Headern, mit Block '# CLAUDIA: HSTS' und dem Header Strict-Transport-Security: max-age=604800 (7 Tage, ohne includeSubDomains, ohne preload). Die Aktion wird nur angeboten, wenn die Prüfung HSTS als fehlend meldet und das Zertifikat keine Warnung hat. Sie ist als nicht vollständig rückgängig markiert (Feld irreversible): Die Oberfläche zeigt einen roten Hinweis und verlangt eine zweite, ausdrückliche Bestätigung; der Server lehnt den Start ohne confirm_irreversible ab. Der Block lässt sich entfernen, die Browser, die den Header gesehen haben, merken sich ihn aber bis zu 7 Tage. Die Wirkung wird per Abruf der Startseite geprüft (Header muss ankommen), sonst wird zurückgerollt.
## a:harden_listing | Ordnerlisten abschalten
Ablauf wie bei den Sicherheits-Headern, mit Block '# CLAUDIA: Ordnerlisten aus' (Options -Indexes in einem IfModule mod_autoindex). Angeboten wird die Aktion nur, wenn die Prüfung 'Öffentlich abrufbare Dateien' (WordPress) eine öffentliche Ordnerliste gefunden hat. Geprüft wird per Abruf, dass die Startseite weiter ausgeliefert wird: Erlaubt der Hoster Options in der .htaccess nicht, antwortet der Server mit 500, und das Programm stellt zurück. Dass die Liste wirklich weg ist, wird nicht einzeln geprüft; dazu die Prüfung wiederholen.
## a:wp_block_xmlrpc | XML-RPC von WordPress sperren
Ablauf wie bei den Sicherheits-Headern, mit Block '# CLAUDIA: XML-RPC gesperrt' (Files xmlrpc.php, Require all denied bzw. Deny from all für Apache 2.2). Angeboten wird die Aktion nur, wenn die Prüfung xmlrpc.php als aktiv gemeldet hat. Danach ruft das Programm xmlrpc.php und die Startseite je einmal ab: xmlrpc.php muss 403, 404 oder 410 liefern und die Startseite darf keinen Serverfehler zeigen, sonst wird zurückgerollt.
## a:harden_perms | Dateirechte auf Sollwerte setzen
Die Aktion arbeitet nur mit Einträgen, die die Prüfung 'Dateirechte' als für die Gruppe beschreibbar gemeldet hat (find -perm -0020 ohne o+w), plus der Konfigurationsdatei, wenn sie für alle lesbar ist. Verweise (Symlinks) werden übersprungen, Pfade müssen _safe_path bestehen (höchstens CHMOD_MAX Stück). Vor jeder Änderung schreibt stat die alten Rechte nach rechte_vorher.txt; dann wird chmod g-w bzw. chmod 440 (nur die Konfigurationsdatei) ausgeführt. Danach ruft das Programm die Startseite einmal ab: Ist sie vorher erreichbar gewesen und danach nicht oder mit HTTP 500 oder höher, werden die Rechte aus rechte_vorher.txt Zeile für Zeile zurückgesetzt. Dateiinhalte werden nie verändert.
## a:joomla_core_reinstall | Joomla-Kerndateien neu einspielen
Auf deinem Computer wird das Original-Paket der Version geladen und gegen die veröffentlichte Prüfsumme geprüft. Nur Dateien, die im Paket stehen und zu _CORE_PATH_RE passen (nie language/), kommen in ein neues ZIP. Auf dem Server werden die aktuellen sha256-Summen bestimmt, nur abweichende Dateien werden ersetzt. Das ZIP wird per base64 über stdin hochgeladen (Prüfsumme wird nachgeprüft), mit unzip entpackt und danach werden die Prüfsummen der ersetzten Dateien erneut mit dem Original verglichen.
## a:wp_update | WordPress aktualisieren
Nach der Sicherung startet das Programm WP-CLI mit dem gewählten PHP, prüft mit core version, dass es läuft, und führt der Reihe nach core update, core update-db, plugin update --all und theme update --all aus. Danach core verify-checksums und eine Liste der Plugins, für die es weiter Updates gibt (meist Premium-Plugins mit eigener Lizenz).
## a:wp_core_reinstall | WordPress-Kern neu einspielen
Nach der Sicherung startet das Programm WP-CLI und führt core download --force --skip-content aus (gleiche Version, aktive Sprache). Das ersetzt nur die Kerndateien, nie wp-content oder wp-config.php. Danach core verify-checksums gegen die Prüfsummen von wordpress.org.
## a:wp_fix_registration | Offene Registrierung abschalten
Sichert die Tabelle options als SQL-Datei (options.sql.gz im Sicherungsordner), setzt dann users_can_register auf 0 und default_role auf subscriber (nur wenn sie administrator war). Zum Schluss liest eine Abfrage beide Werte zur Kontrolle zurück. Die Abfragen laufen mit dem Passwort über stdin.
## a:wp_salts | Neue Schlüssel in der wp-config.php
Die wp-config.php wird gelesen und im Programm (edit_wp_config) mit neuen Zufallswerten für die Schlüssel (AUTH_KEY usw.) versehen. Ändert sich nichts, endet die Aktion. Sonst: Kopie nach ~/claudia-sicherung-wpconfig-<datum>, neue Datei als wp-config.php.claudia-neu schreiben, Rechte der alten übernehmen, prüfen (enthält wp-settings.php, Größe ähnlich) und erst dann mit mv austauschen. Fehlt eine Prüfung, wird die neue Datei wieder gelöscht und nichts verändert. Alle Angemeldeten werden abgemeldet.
## a:wp_disallow_edit | Datei-Editor im Dashboard abschalten
Fügt define( 'DISALLOW_FILE_EDIT', true ); vor der Zeile mit wp-settings.php in die wp-config.php ein (oder ändert false auf true). Der Ablauf ist derselbe wie bei den Schlüsseln: Kopie, neue Datei daneben schreiben, prüfen, mit mv austauschen.
## a:install_security | Sicherheits-Erweiterung installieren
Die Erweiterung muss in der festen Liste stehen (security_tools.json). WordPress: wp plugin install <slug> --activate über WP-CLI, danach is-active und verify-checksums. Joomla: nur wenn der Hersteller eine öffentliche Update-Adresse hat; sie wird vom Programm geprüft (https, feste Form) und an die Joomla-Kommandozeile (extension:install --url) übergeben. Zuerst wird immer eine Sicherung angelegt.
## a:install_backup | Sicherungs-Erweiterung installieren
Gleicher Ablauf wie bei der Sicherheits-Erweiterung, nur mit der Liste backup_tools.json. Die Erweiterung muss dort stehen. WordPress: wp plugin install <slug> --activate über WP-CLI, danach is-active und verify-checksums. Joomla: nur wenn der Hersteller eine geprüfte öffentliche Update-Adresse hat; sonst bietet das Programm den Link zur Store-Seite an. Zuerst wird immer eine Sicherung angelegt. Eine Sicherung selbst legt die neue Erweiterung erst an, wenn du sie im Backend einrichtest.
## a:block_users | Verdächtige Benutzerkonten sperren
Die Konten kommen aus den Befunden (Zeilen mit [ID n]) und werden von dir ausgewählt. Zuerst wird gezählt, ob nach dem Sperren noch ein anderer aktiver Administrator übrig bleibt; sonst bricht die Aktion ab, damit du nicht ausgesperrt wirst. Dann werden die Benutzertabellen gesichert und geprüft. Joomla: block = 1 setzen und die Sitzungen der Konten löschen; die alten Werte stehen in rueckgaengig.sql. WordPress: Rollen auf a:0:{} setzen, Passwort durch einen ungültigen Wert ersetzen, Sitzungen und Anwendungs-Passwörter löschen. Zum Schluss wird gezählt, ob noch ein ausgewähltes Konto aktiv ist.
## a:revoke_tokens | API-Tokens und Anwendungs-Passwörter widerrufen
Nur für die ausgewählten Benutzer. Joomla: Löschen der Zeilen joomlatoken.* in der Tabelle user_profiles. WordPress: Löschen des Eintrags _application_passwords in der Tabelle usermeta. Vorher wird genau diese Tabelle gesichert und geprüft, hinterher gezählt, ob noch etwas übrig ist.
## a:end_sessions | Alle angemeldeten Sitzungen beenden
Joomla: Die Tabelle der Sitzungen wird geleert. WordPress: Die Einträge session_tokens aller Benutzer werden gelöscht. Vorher und nachher wird gezählt. Eine Sicherung gibt es nicht, weil Sitzungen kurzlebig sind. Die Meldung nach dem Lauf enthält die Checkliste für die nächsten Schritte (Passwörter, Datenbank-Passwort, SSH-Schlüssel, Schlüssel der Seite). Das Joomla-Geheimnis (secret in der configuration.php) erneuert CLAUDIA bewusst nicht. Joomla verschlüsselt damit die Zwei-Faktor-Daten (#__user_mfa) und die Passkeys, berechnet daraus die API-Token und den Namen des Sitzungs-Cookies und kennt keinen Übergang vom alten zum neuen Wert. Ein neues Geheimnis würde die Installation und die Zugänge unbrauchbar machen: Zwei-Faktor-Anmeldung und Passkeys funktionieren nicht mehr (auch Administratoren sperren sich aus), alle API-Token werden ungültig. Zurück geht es nur mit der alten configuration.php. Die Daten umzuschlüsseln ist nicht vorgesehen, weil sich das ohne echte Joomla-Installation nicht sicher testen lässt und ein Fehler die Zwei-Faktor-Daten unwiderruflich beschädigen würde. Wer Sitzungen entwerten will, nutzt diese Aktion. Ehrliche Grenzen: Geprüft am Joomla-Quelltext 6.2.0 und 5.4.112 (Stand 12.11.2026), nicht in einer laufenden Installation; Erweiterungen von Drittanbietern und Joomla 3 sind nicht geprüft. Wer das Geheimnis nach einem Datenabfluss von Hand wechselt, muss Zwei-Faktor-Methoden, Passkeys und API-Token danach neu einrichten.
## a:deactivate_extension | Verwundbare Erweiterung ausschalten
Die gewählten Erweiterungen werden in der Tabelle extensions nachgeschlagen (Typ, Gruppe, Name; die Kennung steht in der Befundzeile). Übersprungen werden: vom System geschützte, Joomla-Kern (Autor 'Joomla! Project'), Anmelde- und Zwei-Faktor-Plugins sowie erkannte Sicherheits- und Sicherungs-Erweiterungen. Vor der Änderung wird die Tabelle gesichert; die alten Werte stehen in rueckgaengig.sql. Dann wird enabled auf 0 gesetzt und gezählt, ob noch eine eingeschaltet ist.
## a:disable_api | Joomla-API (Web-Services) abschalten
Es werden alle eingeschalteten Plugins der Gruppen webservices und api-authentication sowie 'Benutzer - Joomla API-Token' in der Tabelle extensions gesucht (vom System geschützte werden übersprungen). Vor der Änderung wird die Tabelle gesichert und geprüft, die Kennungen der Plugins stehen als UPDATE-Befehl in rueckgaengig.sql im Sicherungsordner; kann diese Datei nicht geschrieben werden, bricht die Aktion ab. Dann wird enabled auf 0 gesetzt und gezählt, ob noch etwas eingeschaltet ist. Gelöscht wird nichts, Tokens bleiben erhalten. Nur für Joomla; geprüft nur gegen die Testumgebung (SQLite-Attrappe), nicht gegen jede Joomla-Version.
## a:enable_autoupdate_api | API für automatische Joomla-Updates einschalten
Es werden die Plugins 'Web Services - Joomla-Update' (webservices/joomlaupdate) und 'API-Authentifizierung - Token' (api-authentication/token) in der Tabelle extensions gesucht. Nur wenn sie ausgeschaltet sind, werden genau diese beiden eingeschaltet; weitere API-Plugins bleiben unberührt, es werden keine Tokens angelegt. Vor der Änderung wird die Tabelle gesichert und geprüft, die Kennungen stehen als UPDATE-Befehl in rueckgaengig.sql im Sicherungsordner; kann diese Datei nicht geschrieben werden, wird nichts geändert. Danach wird kontrolliert, dass keines der beiden mehr ausgeschaltet ist. Die Einstellung 'Automatische Updates' selbst wird nie verändert.
## a:wp_deactivate_plugin | Verwundbares Plugin ausschalten
Für jedes gewählte Plugin fragt das Programm mit WP-CLI (plugin is-active), ob es aktiv ist, und fasst nur aktive an. Erkannte Sicherheits- und Sicherungs-Plugins werden übersprungen. Vorher wird die Tabelle options gesichert (dort steht die Liste der aktiven Plugins), und die Befehle zum Wiedereinschalten stehen in rueckgaengig.txt. Nach plugin deactivate wird erneut is-active geprüft.
## a:clear_cache | Cache leeren
Ruft cache:clean der Joomla-Kommandozeile auf. Es werden nur Cache-Dateien entfernt, die Joomla selbst neu aufbaut.
