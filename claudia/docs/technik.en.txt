## g:ablauf | How a command reaches the server
Every check is a short Bash script. The program sends it over the encrypted SSH connection (paramiko) as a single command and reads the output. There is no daemon and nothing stays behind on the server.
- wrap_script: changes into the site folder, sets LC_ALL=C and starts the script with low priority (nice -n 15) so the site does not slow down.
- sq: puts every value that is built into a command in safe quotes (shlex.quote). No file name or value can smuggle in extra commands.
- Runner.sh and SSHRunner.run: run the command, limit time and output size and return output, error text and exit code. A time limit ends hanging commands.
- Ctx.sh: the place where every check starts its scripts. If no server is connected, the check is skipped.
Checks are read-only: they contain only read commands (find, grep, stat, cat, SELECT). Changes to the server happen only through the actions, and only after a preview and your confirmation.
## g:datenbank | How the database is queried
The program does not connect to the database itself. It calls the mysql (or mariadb) program on the server. The credentials are in configuration.php or wp-config.php and are read there (_read_cfg).
- The password is never on the command line (other accounts could see it in the process list). It is passed as the first line on stdin, read into MYSQL_PWD with read and exported.
- _check_vars first makes sure that user, database name and host contain only allowed characters.
- #__ in the SQL is the placeholder for the table prefix and is replaced before the call.
- parse turns the mysql output (tab-separated) into a list of rows. Error texts are stripped of passwords first.
All queries of the checks are SELECT or SHOW. Writing SQL exists in only two actions (delete JCE profiles, switch off registration in WordPress), each after a backup of the affected table.
## g:sicherung | How the backup is made
Actions marked "Backup first" first create a backup in the server's home directory (folder claudia-sicherung-<Datum>, mode 700). Without a valid backup the action stops before anything is changed. Smaller actions create a targeted backup of only the affected files or table instead (_mkdir_backup).
- make_backup first checks the free space (df against du of the site, at least 1.3 times), creates the folder with mkdir -p -m 700, backs up the database (_db_dump_script, password again via stdin) and then the files as tar.gz (without images, cache, tmp and logs; for WordPress without uploads, cache, upgrade).
- Then the archive is checked with tar tzf and the size of both files is verified (too small = abort).
- _home_dir determines the home directory of the server account.
The backup also contains infected files. Never copy it into a publicly reachable folder.
## g:programmupdate | How the program updates itself
At start CLAUDIA asks the project's release page on GitHub in the background (a single https request; without a network nothing happens). Installing only happens after you confirm in the window.
- appupdate.check reads tag_name, release notes and the package CLAUDIA_v<version>.zip; only downloads under github.com/<project>/releases/download/ are accepted. The checksum comes from the package digest or from a line "SHA-256: ..." in the release notes. Without a checksum nothing is installed automatically.
- appupdate.verify_package compares SHA-256, tests the ZIP file, refuses paths with .. or a drive letter and requires claudia/__init__.py to contain exactly the expected version.
- appupdate.backup packs the program folder (without .venv) into %APPDATA%\CLAUDIA\update\sicherung_<version>.zip; earlier backups are replaced.
- appupdate.install writes every file through a temporary file and os.replace. If anything fails, restore puts the backup back and removes newly created files; update.log contains every step.
- start.bat, start.command and install.command are replaced only after the program has ended (finish_code in a detached process), because a running start file would otherwise change in the middle of its run. The same process then restarts CLAUDIA.
- Manual way back: unpack the backup from %APPDATA%\CLAUDIA\update into the program folder (replace files).
## g:haertung | Protection functions and their tests
Everything that creates trust or limits damage is central and covered by tests with proof of effect: if the function is weakened on purpose, the matching test must fail (tests/test_sicherheitsfunktionen.py).
- util.sq quotes every value for the server's shell; db.validate_vars allows only ordinary characters for database name, prefix, user, host and socket and ends with \Z so that even an appended line break is rejected.
- util.parse_xml reads foreign XML only without DOCTYPE/ENTITY, up to 3 MB, and returns None instead of raising on any error. util.digits accepts ASCII digits only.
- util.mask_secrets masks credentials; the value is limited to 4096 characters so the run time stays linear.
- The local server checks Host and Origin, requires the session cookie and the X-Claudia header, limits the request size and serves files only from a fixed list.
## g:dashboard | How the dashboard keeps the history
After every run that completed and after every action that was carried out, CLAUDIA writes a short entry to the file verlauf.json in the data folder. The dashboard only reads this file (and, on request, the stock of backups and quarantine on the server) and changes nothing.
- Only time, site (host and folder), CMS, version, counts, the short titles of warnings and critical findings and carried-out actions with their result are stored. No passwords, no file contents, nothing is sent out. Cancelled runs and runs with an error are not stored.
- In a comparison a finding counts as fixed only if the matching check really ran the second time (field ran). If it was not selected or was skipped, the finding is listed under "not checked", not under "fixed".
- Limits: 400 runs and 600 actions in total; per site the last 12 runs keep their list of findings, older ones only the counts. A broken or foreign file gives an empty history, never an exception; writing and reading run under a lock.
- Hints: last run older than 30 days, no backup or an old backup made with CLAUDIA.
- Follow-up check: after the last successful cleanup (e.g. malicious code removed, accounts blocked) a run three or more days later counts as the follow-up check; the run right after is the success check. If it is missing the hint appears.
- Check backup (verify_backup): read-only gzip -t and tar tzf for the files of a backup; the name must match the program's backups, otherwise nothing is run.
- Export: export_csv defuses cells starting with =, +, - or @; the report writes all texts HTML-safe. support.build leaves out passwords, server address, user names, site folder and the texts of the findings.
- Management: creating a backup, deleting old backups, restoring or deleting quarantine use the same tested actions as "Fixes at the push of a button" (preview of the commands, confirmation, execution). A full backup is deliberately not restored automatically because that overwrites the current state of the site and cannot be undone.
## g:signatur | Digital signature for updates and knowledge data
Program updates and new knowledge data can be checked with an Ed25519 signature. The program knows only the public key (signatur.PUBLIC_KEYS), so it can verify but not sign; the private key is only with the author (tools/signieren.py).
- As long as no public key is entered, the check is not active: the checksum applies unchanged, nothing additional is loaded, and stored knowledge data is never used.
- Once a key is entered, nothing is installed and nothing is taken over without a valid signature. Any deviation is invalid, even a single changed character, an unknown key id or a wrong purpose; verify never raises an exception.
- What is signed is "CLAUDIA-SIG1", the purpose (release or wissen) and the file. So a signature for a package never applies to knowledge data and vice versa.
- Program update: next to CLAUDIA_vX.Y.Z.zip the release page has CLAUDIA_vX.Y.Z.zip.sig; it is loaded only from addresses of this project.
- Knowledge data: wissen/advisories.json with wissen/advisories.json.sig in the repository. A version is taken over only if it is valid JSON with all sections of the bundled version and has a newer date; on every read the signature is checked again.
## g:protokoll | How the status window follows along
During an action every command runs through the wrapper Traced. It reports command and answer to the status window so you can see live what happens on the server.
- mask replaces passwords, download keys and tokens with *** (known secrets and patterns like key=..., token=...) before anything is shown or saved in the report.
- The output is shortened to the last 2,500 characters; a time limit is reported as an error.
## g:extern | How the external mode works
In external mode there is no runner (no SSH). App._connect_external sets conn to {mode: none, external: true, url, host} and calls extern.detect_site; Settings.extern makes Engine.run skip all checks that have neither extern=True nor needs=local.
- Detection: extern.detect() sums weighted signs (generator, folders, headers, cookies, standard addresses). A system counts as detected only with weight 3 or more and a lead of at least 2, otherwise it stays empty.
- Soft 404: gather() requests a random address; if it returns status 200, standard addresses with the same page are discarded, and ext_files counts hits only if the page differs. In addition each file needs a signature in its content.
- Versions: parse_version() reads public sources only; judge_version() uses the existing judges per system and falls back to "info" when the online source is missing (CLAUDIA_OFFLINE: no requests).
- Limits: at most 25 extra requests for extensions, responses are capped at 40 to 60 KB, https only (except local addresses), contents of files found never appear in the result.
## a:backup_now | Full backup
Only the backup step runs (see Basics: Backup). Then the folder name is reported. Nothing on the server is changed except the new backup folder.
## a:fix_permissions | Remove write permission for everyone
For each file from the check: record the permissions with stat in rechte_vorher.txt, then chmod o-w. Links (symlinks) are skipped. Only files that the check itself reported and that are valid paths are touched (at most CHMOD_MAX).
## a:fix_update_perms | Restore write permission for the owner
Like the action before, but with chmod u+rwX: the owner may write again, and enter folders. The old permissions are written to the log rechte_vorher.txt first.
## a:wp_remove_maintenance | End maintenance mode
First it is checked that .maintenance is a normal, small file that contains only $upgrading = <Zahl>;. Then a copy is made and the file is deleted only after the copy succeeded. Afterwards it is checked that the file is gone.
## a:check_updates | Check for updates
Only queries are made, nothing is installed: the Joomla command line (core:check-updates, update:extensions:check), then the list of updates from the database and a cross-check directly at the vendors' update servers.
## a:core_update | Update Joomla
After the backup the program calls core:update of the Joomla command line (time limit 25 minutes). Joomla does the update itself; the program only checks the exit code and shows the output.
## a:update_extensions | Update extensions
After the backup, for each chosen extension the update manifest is loaded on the server with curl (https only) and the download address of the new version is picked out (pick_download). Installation uses extension:install --url of the Joomla command line. Then an SQL query reads the version from manifest_cache as a check. If something fails, up to EXT_RETRIES retries follow (dependencies); extensions whose installer does not run on the command line are reported and not retried. At the end: update:extensions:check and cache:clean.
## a:clean_tmp | Empty temporary folders
First the whole content of the chosen folders is backed up as tar.gz and checked with tar tzf. Only then are the entries deleted (index.html and .htaccess stay). Finally what is left in them is counted.
## a:delete_old_backups | Delete old backups
On the server only folders directly in your home are deleted whose name starts with claudia-sicherung- and which are not links (rm -rf). The name must match the fixed pattern BACKUP_NAME_RE. Logs on your computer can also be deleted (LOG_NAME_RE; the newest log of an action stays).
## a:remove_jce_profiles | Remove suspicious JCE profiles
A SELECT reads the chosen profiles that contain php in their parameters. Standard profiles (SAFE_JCE_NAMES) are not deleted, only reported. Before deleting, the table wf_profiles is backed up as wf_profiles.sql.gz (without only at your explicit request). Then a DELETE with the same conditions and a COUNT as a check follow.
## a:remove_shells | Move web shells into quarantine
You tick in the list which files are moved (_picked_shell_files: only files the check reported, or PHP files in the upload folder, never outside the site). Every path is checked (_safe_path), only regular files count, links do not, at most MAX_FILES per run. Folders without write permission are reported up front and left out. _new_quarantine_dir creates ~/claudia-quarantaene-<Datum>/d with mode 700 (aborts without change if the home directory is inside the site folder) and an access block. _quarantine_header writes the head of the list QUARANTAENE.txt. The script QUAR_MOVE works file by file: the folder must really lie inside the site, determine SHA-256, mode, owner, size and date, write the line to the list, then mv -n into d/<Nr>.q (same file system) or cp -p, compare the checksum and only then remove the original (other file system). Then chmod 600 and a checksum comparison. Each file reports OK, UEBERSPRUNGEN, FEHLER or HINWEIS; finally the files in folder d are counted. Nothing is deleted.
## a:restore_quarantine | Restore files from quarantine
The selection (key q:<Ordner>/<Nr>) is checked with QUAR_KEY_RE; origin path, checksum and mode are read by the script QUAR_BACK itself from the list on the server, not from the selection. Per file: the file is still in d/, the list belongs to this site, the origin path is valid (./..., no ..), the origin folder exists, lies really inside the site and is writable, nothing is at the origin (not even a link) and the SHA-256 equals the list. Then mv -n or (other file system) cp -p, compare checksum, remove the source; afterwards chmod with the original mode, a checksum comparison and an entry in ZURUECK.txt. If a condition fails the script reports UEBERSPRUNGEN with the reason and does not touch the file. _parse_quar_lines evaluates the messages.
## a:delete_quarantine | Delete quarantine folders
The selection (key k:<Ordnername>) is checked with QUAR_NAME_RE. The script QUAR_DEL checks each folder: name starts with claudia-quarantaene-, no slash, folder lies in the home directory and is not a link, the list QUARANTAENE.txt exists and its head names exactly this site folder. Only then rm -rf, followed by a check that the folder is gone. _parse_quar_lines evaluates each message (OK, UEBERSPRUNGEN, FEHLER). Nothing inside the folder is opened or executed.
## a:reset_htaccess | Reset the main .htaccess to the standard
The program reads the .htaccess (_ht_read) and determines the standard file (ht_standard): for Joomla htaccess.txt from the original package of the version (checksum verified), for WordPress the standard block. ht_plan splits the existing file into rules and blocks "# BEGIN/END Name" and keeps own harmless rules and blocks of known plugins; redirects to foreign domains, handler assignments and auto_prepend_file are not kept. The preview is a line comparison old/new. Before writing, the script checks that folder and file are writable, copies the old file as htaccess.vorher (cp -p, then cmp) and writes rueckgaengig.txt. After writing, _fetch_url fetches the https home page; on a server error (5xx) htaccess.vorher is copied back immediately and the request is repeated. Without an https address nothing is changed.
## a:remove_db_code | Remove injected code from the database
_dbcode_plan reads the selected entries (table, column, ID) with the site's database credentials (g:datenbank), delivers the value hex-encoded (at most DBCODE_MAX_HEX) and removes only script and frame blocks that match the check's patterns. Skipped are serialized WordPress values (a:..., s:...), values that are too large and entries without a clear match; the reason is logged per entry. Before any change the program writes an UPDATE statement with the old value for each entry to rueckgaengig.sql and verifies the file (number of statements, checksum); without a valid backup it aborts. Afterwards each entry is read again and compared with the expected new value.
## a:block_php_uploads | Block PHP execution in the images folder
The program first checks that the https address of the site is known and that the folder is not a link. An existing .htaccess is backed up as htaccess.vorher (cp -p, then cmp), and rueckgaengig.txt is written. Then it appends the block HTACCESS_NOPHP or creates the file (Apache 2.2 and 2.4). To test it, it creates a .txt and a .php file with a random name and harmless content and requests both over https (_fetch_url). The block counts as effective only if the text file is served and the PHP file is not executed. Otherwise (or if the request is not possible) it restores the old state. The test files are deleted in every case.
## a:harden_headers | Set security headers
The program first checks that the https address of the site is known and that the .htaccess is not a link. If the block '# CLAUDIA: Sicherheits-Header' is already in it, the action ends without a change. Otherwise the existing .htaccess is backed up as htaccess.vorher (cp -p, then cmp), rueckgaengig.txt is written and the block is appended (ht_block_text). Only the headers that the check reported as missing are set, from a fixed list (nosniff, SAMEORIGIN, strict-origin-when-cross-origin); the Content-Security-Policy is never set. Then ht_block_verdict requests the home page once: if a header does not arrive, if the page returns HTTP 500 or higher, or if it is not reachable, the old state is restored. On nginx (which does not read an .htaccess) the action is not even offered.
## a:harden_hsts | Enable HSTS
Same procedure as for the security headers, with the block '# CLAUDIA: HSTS' and the header Strict-Transport-Security: max-age=604800 (7 days, without includeSubDomains, without preload). The action is offered only if the check reports HSTS as missing and the certificate has no warning. It is marked as not fully reversible (field irreversible): the interface shows a red notice and requires a second, explicit confirmation; the server refuses to start it without confirm_irreversible. The block can be removed, but browsers that have seen the header remember it for up to 7 days. The effect is verified by requesting the home page (the header must arrive); otherwise the change is rolled back.
## a:harden_listing | Switch off directory listings
Same procedure as for the security headers, with the block '# CLAUDIA: Ordnerlisten aus' (Options -Indexes in an IfModule mod_autoindex). The action is offered only if the check 'Publicly accessible files' (WordPress) found a public directory listing. A request verifies that the home page is still served: if the host does not allow Options in the .htaccess, the server answers with 500 and the program restores the old state. That the listing is really gone is not verified separately; run the check again for that.
## a:wp_block_xmlrpc | Block WordPress XML-RPC
Same procedure as for the security headers, with the block '# CLAUDIA: XML-RPC gesperrt' (Files xmlrpc.php, Require all denied or Deny from all for Apache 2.2). The action is offered only if the check reported xmlrpc.php as active. Afterwards the program requests xmlrpc.php and the home page once each: xmlrpc.php must return 403, 404 or 410 and the home page must not show a server error; otherwise the change is rolled back.
## a:harden_perms | Set file permissions to target values
The action works only with entries that the check 'File permissions' reported as writable for the group (find -perm -0020 without o+w), plus the configuration file if it is readable by everyone. Links (symlinks) are skipped, and paths must pass _safe_path (at most CHMOD_MAX of them). Before every change, stat writes the old permissions to rechte_vorher.txt; then chmod g-w (or chmod 440 for the configuration file only) is run. Afterwards the program requests the home page once: if it was reachable before and afterwards is not reachable or returns HTTP 500 or higher, the permissions are reset line by line from rechte_vorher.txt. File contents are never changed.
## a:joomla_core_reinstall | Reinstall Joomla core files
On your computer the original package of the version is downloaded and checked against the published checksum. Only files that are in the package and match _CORE_PATH_RE (never language/) go into a new ZIP. On the server the current sha256 sums are determined and only deviating files are replaced. The ZIP is uploaded as base64 via stdin (the checksum is verified again), unpacked with unzip, and afterwards the checksums of the replaced files are compared with the original again.
## a:wp_update | Update WordPress
After the backup the program starts WP-CLI with the chosen PHP, checks with core version that it runs, and runs core update, core update-db, plugin update --all and theme update --all in turn. Then core verify-checksums and a list of plugins that still have updates (mostly premium plugins with their own license).
## a:wp_core_reinstall | Reinstall WordPress core
After the backup the program starts WP-CLI and runs core download --force --skip-content (same version, active language). This replaces only the core files, never wp-content or wp-config.php. Then core verify-checksums against the checksums from wordpress.org.
## a:wp_fix_registration | Switch off open registration
Backs up the table options as an SQL file (options.sql.gz in the backup folder), then sets users_can_register to 0 and default_role to subscriber (only if it was administrator). Finally a query reads both values back as a check. The queries run with the password via stdin.
## a:wp_salts | New keys in wp-config.php
wp-config.php is read and given new random values for the keys (AUTH_KEY etc.) in the program (edit_wp_config). If nothing changes, the action ends. Otherwise: copy to ~/claudia-sicherung-wpconfig-<date>, write the new file as wp-config.php.claudia-neu, take over the permissions of the old one, check (contains wp-settings.php, similar size) and only then swap it in with mv. If a check fails, the new file is deleted again and nothing is changed. Everyone who is logged in is logged out.
## a:wp_disallow_edit | Switch off the file editor in the dashboard
Inserts define( 'DISALLOW_FILE_EDIT', true ); before the line with wp-settings.php in wp-config.php (or changes false to true). The flow is the same as for the keys: copy, write the new file next to it, check, swap with mv.
## a:install_security | Install a security extension
The extension must be in the fixed list (security_tools.json). WordPress: wp plugin install <slug> --activate through WP-CLI, then is-active and verify-checksums. Joomla: only if the vendor has a public update address; the program checks it (https, fixed form) and passes it to the Joomla command line (extension:install --url). A backup is always made first.
## a:install_backup | Install a backup extension
Same flow as for the security extension, but with the list backup_tools.json. The extension must be in it. WordPress: wp plugin install <slug> --activate through WP-CLI, then is-active and verify-checksums. Joomla: only if the vendor has a verified public update address; otherwise the program offers the link to the store page. A backup is always made first. The new extension creates a backup of its own only after you set it up in the backend.
## a:block_users | Block suspicious user accounts
The accounts come from the findings (lines with [ID n]) and are chosen by you. First the program counts whether another active administrator remains after blocking; otherwise the action aborts so that you are not locked out. Then the user tables are backed up and verified. Joomla: set block = 1 and delete the accounts' sessions; the old values are in rueckgaengig.sql. WordPress: set roles to a:0:{}, replace the password with an invalid value, delete sessions and application passwords. At the end it counts whether any selected account is still active.
## a:revoke_tokens | Revoke API tokens and application passwords
Only for the selected users. Joomla: delete the joomlatoken.* rows in the table user_profiles. WordPress: delete the entry _application_passwords in the table usermeta. Before that, exactly this table is backed up and verified; afterwards it counts whether anything is left.
## a:end_sessions | End all logged-in sessions
Joomla: the sessions table is emptied. WordPress: the session_tokens entries of all users are deleted. It counts before and after. There is no backup because sessions are short-lived. The message after the run contains the checklist for the next steps (passwords, database password, SSH keys, site keys). CLAUDIA deliberately does not renew the Joomla secret (secret in configuration.php). Joomla uses it to encrypt the two-factor data (#__user_mfa) and the passkeys, derives the API tokens and the name of the session cookie from it, and has no transition from the old value to the new one. A new secret would make the installation and its access unusable: two-factor authentication and passkeys stop working (administrators lock themselves out as well), and all API tokens become invalid. The only way back is the old configuration.php. Re-encrypting the data is not provided, because it cannot be tested safely without a real Joomla installation and an error would irreversibly damage the two-factor data. Anyone who wants to invalidate sessions uses this action. Honest limits: checked against the Joomla source code 6.2.0 and 5.4.112 (as of November 12, 2026), not in a running installation; third-party extensions and Joomla 3 are not checked. Anyone who changes the secret by hand after a data leak must set up two-factor methods, passkeys and API tokens again.
## a:deactivate_extension | Switch off vulnerable extension
The chosen extensions are looked up in the table extensions (type, group, name; the identifier is in the finding line). Skipped: system-protected ones, the Joomla core (author 'Joomla! Project'), login and two-factor plugins, and detected security and backup extensions. Before the change the table is backed up; the old values are in rueckgaengig.sql. Then enabled is set to 0 and it counts whether any is still on.
## a:disable_api | Switch off Joomla API (web services)
All enabled plugins of the groups webservices and api-authentication, as well as 'User - Joomla API Token', are looked up in the table extensions (system-protected ones are skipped). Before the change the table is backed up and verified, and the plugin identifiers are written as an UPDATE statement to rueckgaengig.sql in the backup folder; if this file cannot be written, the action aborts. Then enabled is set to 0 and the program counts whether anything is still enabled. Nothing is deleted, and tokens are kept. Joomla only; tested only against the test environment (SQLite stand-in), not against every Joomla version.
## a:enable_autoupdate_api | Switch on the API for automatic Joomla updates
The plugins 'Web Services - Joomla Update' (webservices/joomlaupdate) and 'API Authentication - Token' (api-authentication/token) are looked up in the table extensions. Only if they are switched off, exactly these two are switched on; all other API plugins stay untouched, and no tokens are created. Before the change the table is backed up and verified, and the identifiers are written as an UPDATE statement to rueckgaengig.sql in the backup folder; if that file cannot be written, nothing is changed. Afterwards it is checked that neither is still off. The setting 'Automatic updates' itself is never changed.
## a:wp_deactivate_plugin | Switch off vulnerable plugin
For each chosen plugin the program asks WP-CLI (plugin is-active) whether it is active and touches only active ones. Detected security and backup plugins are skipped. Before that the table options is backed up (it holds the list of active plugins), and the commands to switch back on are in rueckgaengig.txt. After plugin deactivate it checks is-active again.
## a:clear_cache | Clear cache
Calls cache:clean of the Joomla command line. Only cache files are removed that Joomla rebuilds itself.
