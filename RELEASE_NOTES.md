# CLAUDIA 2.18.0 - Single program file and release workflow

- **Single program file without Python setup (Windows, Mac)**: In addition to the existing package, CLAUDIA is available as a single program file: on Windows as an installer (CLAUDIA-Setup-….exe) or as a portable folder with CLAUDIA.exe, on the Mac as CLAUDIA.app (Apple silicon). Python and all components are included; nothing is set up or downloaded at first start. This build does not update itself: the update display points to the release page, "Install update" is not possible there. On uninstall, the Python environment and the program folder are left out (you delete the file or app yourself); reports, connections and settings can be removed as before. Why: Anyone without Python, or who does not want to run a PowerShell script, can open CLAUDIA with a double click. A running program file cannot replace its own program code with an update; an attempt would damage the installation.
- **Release workflow (GitHub Actions)**: The workflow "Release" (button only) runs the tests, builds the package, Windows installer, Windows folder and Mac app, checks every program file with the self-test and then creates the GitHub release v<version> directly: release notes as text, all files as attachments, SHA256SUMS.txt and the line "SHA-256: …" for the checksum of the package. If the tag already exists, the files are replaced and the text is updated. Why: One run delivers all files with matching checksums; nothing can be forgotten or mixed up by hand. The program only installs an update if the release contains CLAUDIA_v<version>.zip and its SHA-256.
- **Release notes: English with a switch to German**: On GitHub the release notes come first in English; German follows in a collapsible block. In the program the display follows the interface language. The text only says what changed technically and why. Why: GitHub has an international audience; the program should still display in the chosen language.
- **Check: Do automatic updates really run?**: New check (Joomla and WordPress). Joomla 5.4 and newer: checks the setting "Automated Updates" and the update source, the API plugins the joomla.org update service needs, the update site, a core update that is available but not installed, offline mode and mail sending, and calls /api of the own site once with and once without a browser identification. Recognizes firewall extensions (e.g. HTProtect, Admin Tools), shows their settings about API, updates and bot filters and entries of their log about /api. WordPress: checks WP-Cron (schedule overdue, wp-cron.php blocked, DISABLE_WP_CRON without cron job) and version control in the folder. New action "Enable API for automatic Joomla updates" (two plugins, with backup and undo file). The action "Disable Joomla API" and the note in the check "API access" now say that this removes automatic core updates from Joomla 5.4 on. Why: The previous check "Can the site be updated automatically?" only checks whether an update in the backend succeeds (permissions, space, PHP). A site can be updated by hand without problems and still never by itself: the joomla.org update service triggers updates through the API, and a firewall, a disabled API or a wrong update source prevent that without anything being noticed.
- **Internal**: New files installer/exe_main.py, tools/build_exe.py, tools/release_body.py, .github/workflows/release.yml, tests/test_exe_build.py, claudia/checks/auto_updates.py, tests/test_auto_updates.py, tests/test_autoupdate_action.py; installer/claudia.iss now also knows /DFrozenApp=1; the old workflow build-windows.yml is removed (replaced by release.yml). Why: One single way to a release instead of two separate ones.

# CLAUDIA 2.18.0 - Einzelne Programmdatei und Release-Workflow

- **Einzelne Programmdatei ohne Python-Einrichtung (Windows, Mac)**: Zusätzlich zum bisherigen Paket gibt es CLAUDIA als einzelne Programmdatei: unter Windows als Installer (CLAUDIA-Setup-….exe) oder als tragbarer Ordner mit CLAUDIA.exe, auf dem Mac als CLAUDIA.app (Apple Silicon). Python und alle Bausteine sind enthalten; beim ersten Start wird nichts eingerichtet oder geladen. Diese Fassung aktualisiert sich nicht selbst: die Update-Anzeige verweist auf die Release-Seite, "Update installieren" ist dort nicht möglich. Bei der Deinstallation entfallen die Python-Umgebung und der Programmordner (die Datei bzw. App löscht man selbst); Berichte, Verbindungen und Einstellungen lassen sich wie bisher entfernen. Warum: Wer kein Python hat oder kein PowerShell-Skript starten möchte, kann CLAUDIA mit einem Doppelklick öffnen. Eine laufende Programmdatei kann ihren eigenen Programmcode nicht durch ein Update ersetzen; ein Versuch würde die Installation beschädigen.
- **Release-Workflow (GitHub Actions)**: Der Workflow "Release" (nur auf Knopfdruck) führt die Tests aus, baut Paket, Windows-Installer, Windows-Ordner und Mac-App, prüft jede Programmdatei mit dem Selbsttest und legt dann direkt den GitHub-Release v<Version> an: Release Notes als Text, alle Dateien als Anhang, SHA256SUMS.txt und die Zeile "SHA-256: …" für die Prüfsumme des Pakets. Existiert das Tag schon, werden die Dateien ersetzt und der Text aktualisiert. Warum: Ein Lauf liefert alle Dateien mit zueinander passenden Prüfsummen; von Hand kann dabei nichts vergessen oder vertauscht werden. Das Programm installiert ein Update nur, wenn der Release CLAUDIA_v<Version>.zip und dessen SHA-256 enthält.
- **Release Notes: Englisch mit Umschaltung auf Deutsch**: Die Release Notes stehen auf GitHub zuerst auf Englisch, Deutsch folgt in einem aufklappbaren Block. Im Programm richtet sich die Anzeige nach der Sprache der Oberfläche. Der Text nennt nur, was technisch geändert wurde und warum. Warum: Auf GitHub liest eine internationale Leserschaft; das Programm soll trotzdem in der gewählten Sprache anzeigen.
- **Prüfung: Laufen die automatischen Updates wirklich?**: Neue Prüfung (Joomla und WordPress). Joomla ab 5.4: prüft die Einstellung "Automatische Updates" und die Update-Quelle, die API-Plugins, die der Update-Dienst von joomla.org braucht, die Update-Quelle, ein bereitliegendes, aber nicht installiertes Kern-Update, Offline-Modus und Mailversand und ruft /api der eigenen Seite einmal mit und einmal ohne Browser-Kennung auf. Erkennt Firewall-Erweiterungen (z. B. HTProtect, Admin Tools), zeigt ihre Einstellungen zu API, Updates und Bot-Filtern und Einträge ihres Protokolls zu /api. WordPress: prüft WP-Cron (Zeitplan überfällig, wp-cron.php gesperrt, DISABLE_WP_CRON ohne Cronjob) und Versionsverwaltung im Ordner. Neue Aktion "API für automatische Joomla-Updates einschalten" (zwei Plugins, mit Sicherung und Rückgängig-Datei). Die Aktion "Joomla-API abschalten" und der Hinweis in der Prüfung "API-Zugang" nennen jetzt, dass damit die automatischen Core-Updates ab Joomla 5.4 entfallen. Warum: Die bisherige Prüfung "Lässt sich die Seite automatisch aktualisieren?" prüft nur, ob ein Update im Backend gelingt (Rechte, Platz, PHP). Eine Seite kann sich so problemlos von Hand aktualisieren lassen und trotzdem nie von selbst: Der Update-Dienst von joomla.org stößt die Updates über die API an, und eine Firewall, ein abgeschalteter API-Zugang oder eine falsche Update-Quelle verhindern das, ohne dass etwas auffällt.
- **Intern**: Neue Dateien installer/exe_main.py, tools/build_exe.py, tools/release_body.py, .github/workflows/release.yml, tests/test_exe_build.py, claudia/checks/auto_updates.py, tests/test_auto_updates.py, tests/test_autoupdate_action.py; installer/claudia.iss kennt jetzt zusätzlich /DFrozenApp=1; der alte Workflow build-windows.yml entfällt (ersetzt durch release.yml). Warum: Ein einziger Weg zum Release statt zwei getrennter.
